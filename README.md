# 能量账本 · Energy Ledger

一本会自我校准的私人饮食账本。本地优先：没有账号、没有云端、没有社交；数据只写入当前浏览器的 `localStorage`。

当前版本：**v4.4**（v4.3 基础上：维护入口口令改为加盐 PBKDF2 派生 + 设备令牌、五张连刮、券包空态「怎么拿券」动态面板）

---

## 一、怎么跑

### 方式 A：本机服务（推荐，功能最全）

```bat
启动账本.bat
```

或手动：

```bash
python server.py          # 默认 http://127.0.0.1:8787
python server.py --lan    # 同一 Wi-Fi 的手机也能访问
```

需要 Python 3（仅标准库）。本机服务会转发 AI 视觉请求，绕过浏览器跨域限制。

### 方式 B：单文件静态版（发给别人 / 部署）

```bash
python build_standalone.py
```

生成 `energy-ledger-standalone.html`（把 CSS 与全部 JS 内联进一个文件），双击即可用，也可上传到任意静态主机（GitHub Pages 等）。该文件带 `ledger-standalone` 标记，会自动注销旧 Service Worker，避免缓存串版本。

### 方式 C：多文件开发

直接用 `index.html` + `assets/*.js`，通过任意静态服务器打开。修改 `index.html` 里的 `?v=` 版本号可绕过缓存。

## 三、v4.2 新增（当前版本）

### 1. 「今天吃什么」三餐推荐

入口固定在今日账页「今天吃什么」卡片里，不在子菜单；今天没有记录时也直接显示，并写明「今天还没记录，按全天预算分配」。

- **三段**：早 / 午 / 晚。每餐 **5 套**搭配，每套 **3–5 道**（主食 + 蛋白 + 蔬菜 + 汤或水果），每套显示菜名、份量、热量与蛋白合计。
- **组合池 540 组**（每餐 180 组），来自 5,187 条菜名库 + 1,046 条原料；不是随机堆菜。
- **预算分配**：有记录时按剩余预算，无记录时按全天预算；早 ~25%、午 ~40%、晚 ~35%。
- **真实计算**：按目标热量缩放份量（0.6–1.5 倍），份量取 30g/10g 整数；合计热量与蛋白由食材条目累加，不手写。
- **换一换**：记录已看过的组合（`reco.seen`，最多保留 500 条），同一天连点不会重复；QA 连点 10 次得到 50 套全部唯一。
- **偏好**：素食 / 低碳 / 高蛋白 / 清淡，选中后写入 `reco.prefs`，刷新后保留；素食筛选会剔除肉禽水产。
- **一键操作**：每套可「加入购物车」或「记入这一餐」；底部「随便来一套」一次给完整三餐，也可单独换某一餐。
- **诚实标注**：界面固定写「规则组合 · 估算值」；食材营养是估算，不冒充精确值。

> 推荐是**规则组合 + 估算值**，不是营养师方案，也不针对疾病、孕期、过敏等特殊医学情况。

### 3. 彩票（每日 1 张，概率真实实现）

发卡条件（三选一即可）：当天 ≥ 1 条记录，且满足以下任一：

1. 当日摄入在预算 **85–105%**；
2. 当天有体重记录；
3. 当天有训练记录。

每天最多 1 张，不累积、不额外加发；同一天再记账不会多抽。

| 档位 | 概率 | 子项与权重 |
|---|---|---|
| 普通 | 80% | 账本语录 30% · 纪念小戳 25% · 想吃清单解锁 20%（只展示，不计热量） · +80 kcal 弹性额度 15% · 图鉴点亮卡 10% |
| 稀有 | 17% | 纸纹/皮肤配色 20% · 印章样式 20% · 请假条 20% · +150 kcal 弹性额度 20% · **放纵日通行证 20%** |
| 传说 | 3% | 烫金对账单封面 35% · 勋章节 30% · 整套皮肤 25% · 特殊纪念章 10%（附带 1 张 streak 复活券） |

- **保底**：连续 7 张未出稀有及以上，第 7 张强制进入稀有池（QA 用 `miss=6` 抽 60 次，60 次全部稀有）。
- **热量额度闸门**：每周累计上限 **300 kcal**；超出上限不再发额度，改发外观类奖励（皮肤、印章、封面等）。
- **额度券**：当日有效，过期自动失效并提示「1 张弹性额度已过期失效」；不可攒、不可跨周。
- **期望值**：0.8 × 15% × 80 + 0.17 × 20% × 150 ≈ **15.98 kcal/天**（约 16 kcal/天），README 按真实权重写明，不夸大中奖率。
- **合规红线**：不付费、不真钱、无外部奖品、不诱导连抽、不做「差一点就中」的假提示；奖池只与健康目标兼容（额度、请假条、外观、展示型想吃清单）。

### 4. 放纵日：只从彩票出，不提供手动申请

- 「放纵日通行证」只在稀有档掉落（稀有 17% × 20% ≈ 单张 3.4%）；当周可用一次，不可叠加。
- 使用后当天预算 **+15%**，超支部分盖章「**经批准**」而不是「超支」，且**不打断连续达标**。
- 未使用通行证的普通超支仍然破 streak（QA：同一天超支，批准后 streak 1，撤销批准后 streak 0）。

### 6. 刮卡动效参数（照实现）

- 入场：卡片右侧滑入 250 ms ease-out；纸纹底 + 金线压边；小字「今日已核 · 可刮」。
- 刮除：canvas 银色涂层带颗粒噪点；笔刷半径 24 px；碎屑粒子同时 ≤ 8 个；触控震动 8 ms（支持时）；刮开 ≥ 60% 自动补完，残余碎散淡出。
- 开奖：普通 400 ms 轻弹 + 盖章；稀有 300 ms 金边流光 + ≤ 40 粒子 + `rotateY` 翻面；传说 800 ms 全屏微光 + 纸纹转金 + 凹陷压印，不做满屏烟花。
- 收尾：正面停留约 1 秒出现「存进钱包」；额度券显示到期。
- `prefers-reduced-motion`：退化为淡入淡出，无粒子、无翻面，刮卡仍可操作（QA 实测 `animationName = none`、粒子 0、仍能刮开）。
- 性能：粒子只动 `transform / opacity`，刮层只在刮卡时渲染。

### 7. 数据键（不破坏旧数据）

主键仍是 `energy-ledger.v2`，新增字段：

- `reco = { prefs: { veg, lowcarb, highprotein, light }, seen: [] }`
- `wallet = { credits: [{ id, kcal, kind, expire, label, used, usedAt, from }], applied: [] }`
- `scratch = { lastEarnedDate, count, miss, log, card, last, weeklyKcal, pass: { week, used } }`
- `cheatDays = { history: [] }`、`leaveDays = []`、`wishlist = []`
- `skins = { active, unlocked, theme, stamp, cover, unlockedCos }`
- `codex = { lit: [] }`、`bank = { loans: [] }`、`revive = []`
- `tasks = { date, list }`、`anti = { since, lastPrompt, date }`

导入导出 JSON 会包含以上全部字段；旧备份导入后由 `normalizeDB()` 兜底，不需要迁移。

| 类别 | 条数 | 类别 | 条数 |
|---|---:|---|---:|
| 主食 | 222 | 蔬菜 | 253 |
| 肉禽 | 163 | 水果 | 45 |
| 水产 | 88 | 坚果 | 18 |
| 蛋奶 | 26 | 调味 | 24 |
| 豆制品 | 35 | 饮品 | 44 |
| 零食 | 70 | 半成品 | 58 |
| **合计** | **1,046** | | |

每条的字段：名称、别名/口语叫法（如「米饭 → 白米饭 / 大米饭 / 饭」）、每 100g 热量与蛋白/碳水/脂肪/纤维、2–3 个常见份量（如「1 碗 · 150g」「1 个 · 50g」）、拼音全拼与首字母。点份量 chip 直接加入这一餐的购物车。

**数据口径（必须看清）**：营养值是按常见品类与家常配比换算的**估算值**，不是逐条官方检测数据，也没有引用《中国食物成分表》的具体条目。界面在搜索框下方固定标注「营养值为估算值……非逐条官方检测数据」。

**性能**：食材数据不写入 `localStorage`；多文件模式下按需加载 `assets/foodlib-data.js` 并缓存到 IndexedDB（库 `energy-ledger-foodlib`），单文件模式直接内联。记录本身仍然只写 `localStorage`（主键 `energy-ledger.v2`）。

| 指标 | 实测 |
|---|---|
| 食材条数 | 1,046 |
| 菜名库（「只知道菜名？」） | 5,187 条，运行时由 `buildDishCatalog()` 计算 |
| 首次载入（单文件内联，`ensure()` 计时） | 28 ms |
| 首次载入（多文件懒加载，本地服务） | 33 ms |
| 二次打开（IndexedDB 缓存命中） | 8 ms |
| 单次搜索耗时（200 次平均，`mf`） | 0.13–0.16 ms |
| 单次搜索耗时（200 次平均，空查询） | 0.02 ms |

搜索支持：中文名、别名、拼音全拼（`xihongshi`）、拼音首字母（`mf` → 米饭；`fqcd` → 番茄炒蛋）；类别筛选；最近使用与收藏置顶。

### 2. 界面质感：像一本账本

- 今日页改为「账页」：左侧大号日期（楷体手写风格数字）+ 年月/周 + 账页编号，右侧逐条流水，热量按「项目 / 支出 kcal」两列对齐，底部结余用双线分隔。
- 纸面：细横线账页格 + 极轻纤维纹理 + 左侧装订线；暗色模式改为深墨绿纸面，不叠加噪点。
- 印章：当天有记录时盖「已核」章，超预算盖「超支」章（双圈 + 轻微旋转做旧）。
- 可用性红线：正文对比度按 WCAG AA 校验；份量/分类等触控目标 ≥ 38px；360×640 下今日、记一餐、月度账页均无横向溢出（实测 `scrollWidth - innerWidth = 0`）。
- 暗色跟随系统（`prefers-color-scheme`），也可在设置里手动切换。

### 3. 另外加的 4 个功能与理由

| 功能 | 入口 | 为什么加 |
|---|---|---|
| 月度账页（翻页） | 今日页「本月账页」 | 只看今日容易忽略整体节奏；翻页式月历一屏看完一个月的达标/超支分布，比横向滚动热力条更接近纸质账本 |
| 月度合计 + 分类占比 | 月度账页内 | 回答「钱花在哪」：本月摄入、记账天数、日均，以及主食/肉禽/蔬菜等前 5 类的热量占比 |
| 常用食物收藏 + 最近使用 | 记一餐列表 | 每天重复的食物占大多数；收藏和「最近吃过」让高频食物两次点击内完成，不用反复搜索 |
| 导出月度对账单 PNG | 月度账页「导出月度对账单」 | 复诊或找教练沟通时需要一份看得懂的图；图片在本机 canvas 生成，不上传 |
| 离线可用提示 | 顶部小条 | 本地优先的产品要明确告诉用户：断网时账本仍可用，数据只在本机 |

（「复制昨天」沿用既有功能，本次未改。）

### 4. 本次真实使用回归发现并修复的问题

| # | 问题 | 影响 | 状态 |

| 备份与迁移 | JSON 导出/导入补齐 v3.2 新数据；照片不进入 JSON，需手动另存 | 设置 → 数据 |
| 单文件部署 | `extras.js` 一并内联；构建后仍为单个 HTML | `python build_standalone.py` |

### 新增数据键（都避开已有键）

localStorage 主键仍是 `energy-ledger.v2`（未改键、未迁移旧数据）。新增的是同一对象里的字段：

- `lifts = [{ id, date, exercise, sets, weight, reps, note, createdAt }]`
- `recipes = [{ id, name, at, items: [{ name, grams, per100: { kcal, p, c, f, fib } }] }]`
- `shopping = { recipeId, recipeName, at, items: [{ name, grams, checked }] } | null`
- `wearable = { 'YYYY-MM-DD': { steps, sleepH, source, at } }`

照片不在 localStorage，单独的 IndexedDB：

- 数据库：`energy-ledger-photos`
- 对象仓库：`photos`（keyPath `id`，索引 `date`）
- 记录：`{ id, date, at, name, w, h, bytes, stored, data }`，`data` 为压缩后的 JPEG data URL

`normalizeDB()` 只做内存兜底；旧数据在没有任何保存动作前不会被改写。下一次正常保存才会补齐默认字段，已有 `entries / weights / cycle / settings` 等字段原样保留。

### 周报「达标天数」口径

`记录且当天摄入在预算 ±10% 内`。体重变化取该周趋势的首尾差；训练次数按“有力量或有氧记录的独立日期”计数，不是组数。

### 进度照片的配额与边界

- 压缩目标：最长边 1080 px，JPEG 质量 0.82，白色背景（透明 PNG 不会变黑）。
- 写入前用 `navigator.storage.estimate()` 检查剩余配额；接近 98% 时拒绝写入并提示先清理。
- 捕获 IndexedDB 的 `QuotaExceededError`，不会破坏已有照片。
- 非图片文件、HEIC 等浏览器不能解码的格式会提示转换；超大图只缩小尺寸，不会无限占用。
- 照片只在本机，浏览器清数据/换浏览器会丢失；导出 JSON 不包含照片。

### 可穿戴导入支持字段

| 格式 | 支持 | 不支持 / 说明 |
|---|---|---|
| Apple Health XML | `HKQuantityTypeIdentifierStepCount`（按日 + 来源取最大值，避免手表和手机重复计数）、`BodyMass/BodyWeight`（kg/lb）、`SleepAnalysis`（不含 Awake/InBed，按结束日汇总小时） | 心率、卡路里、锻炼、站立、血氧等只显示为“未导入类型”；Apple 导出文件通常很大，浏览器解析需要内存 |
| 华为运动健康 CSV | 列名含 `日期/date/时间` + `步数/steps` + `体重/weight` + `睡眠/sleep`；体重支持 kg/斤/lb（按表头判断）；睡眠支持 `7.5`、`7:30`、`7h30m`、`分钟` | 列名必须能识别；多设备重复记录不做去重；心率、卡路里等列不导入 |

冲突处理：预览按日期列出“现有值 → 新值”，每个冲突项都有「跳过」勾选；不勾选即覆盖同日值。导入只写体重、步数、睡眠，不改饮食/运动/周期。

### 为什么不做云同步

项目没有后端、没有账号体系。做“云同步”只能做成假的（把数据塞进某个第三方存储或让用户手动贴 JSON），既不可靠也不符合“本地优先”的承诺。v3.2 的做法是：

1. 设置 → 数据 → 导出 JSON（含所有新数据结构，不含照片）
2. 新设备打开账本 → 导入 JSON
3. 照片在旧设备的「进度照片」里逐张另存，或在新设备重新上传
4. 不提供自动覆盖、自动合并或后台同步

### 1. 三餐组合池 3,540 组

- 早餐 1,180 / 午餐 1,180 / 晚餐 1,180，共 **3,540** 组，全部唯一。

### 4. 里程碑发券与上限

- 连续达标 3 / 7 / 14 / 30 天分别一次性发 **+1 / +2 / +3 / +4** 张（累计 10 张），每个里程碑只领一次，重复调用不发放。
- 券可存，**上限 10 张**，超出提示「已达上限，本次超出未发放」；券无过期。
- 每日仍 1 张基础卡（当天记一餐后发放），不与里程碑叠加成额外卡。
- 每周热量额度上限 **300 kcal** 不变；维护模式例外（见下）。超出上限的热量奖品自动改发外观类。
- 期望值：每日 1 张 → 每周约 7 抽；+80 额度出现率约 8.33%/抽、+150 约 0.39%/抽，热量期望约 **51 kcal/周**，正常玩法几乎不会触顶 300；顶级皮肤单抽 **2.25%**，平均约 44 抽出一套，7 抽/周下约每周 14.6% 至少出一套。

### 6. 皮肤图鉴与维护入口

- 图鉴：30 套网格；未解锁 `grayscale + opacity .5 + 锁图标`，预览也做灰度；已解锁显示彩色缩略图与来源；筛选全部/已解锁/未解锁；收集率 x/30；点已解锁可预览并「设为当前」，点未解锁只说明获取方式；360×640 两列无横向溢出。
- 维护入口：设置页「维护」区块，统一显示为「维护模式」。口令不落明文，页面只保存加盐 PBKDF2（SHA-256、10,000 次迭代）派生值；首次通过后写入本机令牌 `el.mt.token`（32 字节随机 + 时间戳）与会话校验键 `el.mt.key`，同一浏览器刷新后免密进入；令牌缺失、清空或被篡改（派生键不符）都会回到口令输入。错误只累计本机尝试次数 `el.mt.attempts`，不锁死，也不提供跨设备记住能力。正确后一次性发 **10,000 张券**（不设 10 张上限）、热量额度不封顶、30 套皮肤与全部外观（48 键）直接解锁，顶部显示可退出的标记条；数据写入独立键 `energy-ledger.dev`，真实账本 `energy-ledger.v2` 读写互不可见，退出后恢复真实进度。
- 派生值由 `tools/gen_maint_credential.py` 在构建期生成（口令从环境变量 `LEDGER_MAINT_PW` 或一次性临时文件读入，临时文件读后删除），提交的只有 `assets/maint-credential.js` 中的盐、迭代次数与派生值，不含口令原文。
- **安全声明（如实标注）**：这是「挡随手翻源码」的门槛，不是保密措施。PBKDF2 派生值可被字典暴力枚举，短口令几分钟内可解；不要指望它保护任何敏感数据。

## 九、已知限制

- **没有云同步**：无后端、无账号。换设备只能导出 JSON → 导入；照片在 IndexedDB，不在 JSON 里，需要逐张另存或重新上传。
- **PIN 不是加密**：只遮挡随手打开的人；同一台电脑的熟练用户仍可读取 `localStorage`。清除浏览器数据会连同账本一起清除。
- **AI 教练需要 API Key**：静态版可直连通义千问（DashScope）；智谱 / OpenAI 需要本机代理。回答是估算，不是医疗建议。
- **性别文案**：男性版是按对等语义新写的通用健身/营养表述；专业场景建议由专业人士再润色。
- **照片配额**：IndexedDB 仍受浏览器配额限制；清理照片只删照片，不动账本。HEIC 需要先转 JPEG/PNG。
- **可穿戴解析**是“常见字段”适配：Apple 步数按来源取最大、睡眠按结束日归档；华为 CSV 依赖列名识别，不做多设备去重。心率、卡路里、锻炼不导入。
- **1RM 是估算**：Epley 公式只适合比较同一动作的长期趋势，不适合测试极限重量。
- **周报口径**：达标天数 = 记录且摄入在预算 ±10%；训练次数按独立日期计数。上周/本周的预算使用当前体重与目标，不会回溯历史预算。
- **营养数据全部是估算**：1,046 条食材是按常见品类与家常配比换算的近似值，不是逐条官方检测数据，也没有引用《中国食物成分表》的具体条目；界面已固定标注。
- **菜名不在原料搜索里**：5,187 道菜名只在「只知道菜名？」入口按菜名估食材与热量，记一餐的食物列表只搜 1,046 条原料，避免两种条目混在一起影响选择。
- **拼音首字母**：已改为词组级拼音（番茄 → `fq`），但多音字仍可能个别不准；可直接输入中文或全拼（`xihongshi`）。
- **单文件体积**：v4.3 为 1.63 MB（内联 94 KB 食物数据 + 5 张顶级底图），首次打开需下载整包；多文件模式则按需加载并缓存到 IndexedDB。
- **部署**：`deploy/index.html`、`docs/index.html`、`docs/energy-ledger-standalone.html` 三处都是同一份单文件，本次已同步；`docs/assets/*` 为多文件模式保留，不影响 Pages 单文件入口。
- **v4.3 组合池是内存懒生成**：每次打开推荐时重新生成（约 100 ms），不在设备上持久化；因此不同会话的「同一天」推荐可能不同，只有当前会话保证不重复。
- **里程碑溢出即作废**：券袋已满 10 张时，新里程碑仍会被标记为已领取但不再补发；这是「超出不再累加」的直接结果，没有找回机制。
- **传说档权重会动态漂移**：已解锁的顶级皮肤退出池子，剩余项按比例分权重；抽取前 5 套时的实际命中率高于 15%。1,000 次抽样针对新号（5 套全未解锁）模型。
- **维护入口不是安全功能**：页面只保存加盐 PBKDF2 派生值，但派生值可被字典枚举，短口令几分钟可解；设备令牌只是本机便利，不构成授权。维护数据只在本机 `energy-ledger.dev`，不参与真实账本统计，不要在其中存放敏感信息。
- **顶级底图体积**：5 张 webp 共约 537 KB，单文件版约 1.63 MB；慢网首次打开会明显变慢。

### 建议但未做（按优先级）

1. 云同步 / 多设备合并：需要账号与后端，违背本地优先定位，暂不做。
2. 照片导出打包（ZIP）：需要额外依赖或复杂压缩，当前只支持逐张另存。
3. 可穿戴更多字段（心率、睡眠分期、锻炼）：解析成本高且与现有模型无对应入口。
4. 训练容量/周计划与图表：当前只做 PR 与 CSV，不做课表。
5. 菜谱营养分摊（按份数而非克数）：当前所有克数都按整份计。
